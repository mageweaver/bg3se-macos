# Session report — 2026-08-20

76 commits. Parity 92.9% → **95.4%** (267/280).

The parity number is the least interesting result. Most of the work was
**correctness in APIs already credited as working** — features that returned
confidently wrong answers rather than failing, which no test was catching
because wrong-looking-right is indistinguishable from right without an
independent oracle.

## The headline fix: BG3SE made multiplayer unstartable

`COsiris::InitGame()` returns a value in x0. The hook declared it `void`, so it
discarded the original's result, ran its own post-call work (which clobbers x0)
and returned garbage. The game checks that value when creating a session.

Found by bisection, not by reading — the signature *looks* right:

| Configuration | Multiplayer |
|---|---|
| vanilla (dylib moved aside) | works |
| BG3SE, network hooks off | fails |
| BG3SE, all code patches off | works |
| BG3SE, StaticData hooks off | fails |
| BG3SE, Osiris hooks off | works |
| BG3SE, only InitGame hook off | works |
| BG3SE, all hooks, fix applied | **works** |

`COsiris::Event` had the same defect and was fixed alongside.

## Replication: mechanism identified, one observation short

`SyncBuffers` — the Windows mechanism — is **dead on this build**. A sampler
(self-verified to actually run, because a silent no-op looks exactly like a
negative result) never saw any of 582 pools populated, including with a console
client connected over crossplay and replication visibly working.

The real path is `esv::replication::ReplicationSystem::ReplicateToPeer`, now
resolved and wired. `Replicate` is deliberately **not credited**: it works
mechanically but its effect is unverified, and crediting on mechanism alone is
what produced several retractions below.

## What went wrong, and the pattern

Five crashes, all mine:

1. Trusted `HasRawComponent` as a safety check; it false-negatives, so a
   component was removed from the player and the renderer died.
2. Assumed `CreateComponent` was the safe half of a round trip.
3. Shipped a C++ `try/catch` on an unverified theory — the stub *calls*
   `std::terminate`, so there was nothing to catch.
4. + 5. Called `StopReplicateWith` with the wrong convention, twice. It is a
   *static* member; C++ mangling does not distinguish static from non-static,
   so the demangled name is identical either way.

Plus a one-byte buffer overflow in my own diagnostic code.

Three retractions, each from asserting before measuring:

- Claimed `RemoveComponent` returned `bool`; the mangled name proves `void`.
- "Fixed" the ActionResource stride to `0x180` and reported the prediction met —
  it was `0x60`. `0x180` is `4 × 0x60`, so every read landed on a boundary and
  looked perfect while returning one resource in four.
- Argued a stride was corroborated by pointer deltas the port itself computes
  from that stride.

**The pattern:** every failure came from reading a name, a number, or a struct
and inferring behaviour. Every success came from reading instructions — the
epilogue for return types, the prologue for calling conventions, the call sites
for layout — or from comparing against an independent oracle (Osiris position vs
component read; bank `count` vs measured record boundaries).

Corollary learned the hard way: **verify the instrument first.** An audit script
with a nested-namespace bug, an entropy-based stride probe, and a sampler that
might silently no-op all failed in the same direction as the defects they were
looking for.

## Still open

- `Replicate` — one observation with a peer connected.
- `StaticData.GetSources` — three offset theories, all wrong; needs the offset
  read from a function that touches the field, not derived from a struct.
- `AddAttribute` — the documented unlock has **zero callers**; worse than recorded.
- `BeginPathfinding` — full ABI recovered, blocked on constructing
  `UnprocessedSettings`.
- `GetGlobalSwitches`, `GetDialogManager`, `StaticData.Create` — lookups are
  tractable, the Windows-derived object graphs are not, and `GlobalSwitches` is
  *proven* not to transfer (`SkipSplashScreen` 0x6AC here vs 0x13E6 there).
- Replication ×3 — multiplayer, excluded by scope.
- `entity:OnChanged` — likely impossible; the engine exposes no
  component-modification signal.
