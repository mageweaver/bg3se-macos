## Design decisions (E2.0)

1. **One coarse gate through E2.3.** Both VMs share the existing single recursive `lua_gate`. Correctness first: no lock-ordering hazards, no cross-VM deadlock surface, and cross-VM message delivery (E2.5) can hold the one gate while touching both states. Per-VM gates are a *later* optimization, taken only if profiling shows contention, with a fixed server-before-client lock order. This matches the plan's "create both states behind lua_gate" wording.
2. **`LuaRuntime` struct** (`src/lua/lua_runtime.h`): `{ _Atomic(lua_State *) L; LuaContext context; uint32_t generation; bool alive; }` — the `L` field is atomic so non-gate threads can pre-check liveness; `generation`/`alive` stay gate-only. Two private instances live in `lua_runtime.c`, reached via `lua_runtime_server()`/`lua_runtime_client()`/`lua_runtime_state_for(ctx)`. The single-VM fallback in `state_for` is compatibility-only: the first client registration latches dual-VM mode, after which a dead exact-context runtime resolves to NULL — never the other VM. Every module cache in Category 1 is replaced by a pointer to the owning runtime (or a context enum resolved through it). Registry-ref holders (Category 2) gain `{ LuaRuntime *owner; uint32_t generation; }` and validate before resolving — the pattern `callback_registry.c` already uses, extended with the generation check.
3. **Generation semantics:** incremented on every state reset/close. A ref whose stored generation mismatches its owner's current generation is dead — unref attempts and callback dispatch both become no-ops with a warn-once, never a resolve against a reincarnated state.
4. **Shutdown order:** cancel timers → drain/clear queues → drop module dispatch barriers (entity events, functor hooks, log callback) → unregister runtimes (generations bumped, pointers retracted) → close client_L → close server_L, all under the gate, so any blocked waiter re-resolves to a dead runtime.
5. **Single-VM preservation through E2.2:** until E2.3, both bootstraps continue loading into server_L and client_L stays script-empty, so the 11-mod compat matrix must be bit-identical. The E2.2 gate (repeated init/shutdown, balanced registries, no stale pointers, zero mod regressions) runs before any routing changes. **E2.2 routing caveat:** registering the client VM latches dual-VM mode, flipping `state_for(CLIENT)` to the script-empty client VM — but IMGUI/hotkey refs created by mods still live in the server VM's registry until E2.3 splits bootstraps. E2.2 must therefore either defer client-owned subsystem re-routing (keep them resolving the ref-owning VM) or land Category-2 owner tags first; dispatch-by-context alone would mis-resolve refs against the empty client registry.
6. **Static gate (plan requirement):** `tests/harness/test_lua_state_ownership.py` walks `src/` for `static lua_State *` declarations outside `lua_runtime.[ch]`, so new unowned global Lua references fail CI as they're introduced. **`ALLOWLIST = set()` — the gate is closed and must stay empty.**
